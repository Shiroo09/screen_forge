# ScreenForge — Rust port

Reference implementation of ScreenForge in Rust. Starts with the parts that are
pure logic, where behaviour can be pinned byte-for-byte against the C# original
before anything platform-specific is rewritten.

Measured baseline for why this exists: the shipping C# app idles at
**~118 MB working set / 516 MB private** (`Get-Process ScreenForge`), which is
framework overhead a tray app shouldn't carry.

## Status

| Crate | C# source | State |
|---|---|---|
| `sf-gif` | `ScreenForge/Gif/Encoder/*`, `Gif/FrameStore.cs` | Ported, byte-identical output verified |
| `sf-settings` | `ScreenForge/Settings/AppSettings.cs` (+ language/modifier helpers) | Ported, reads & writes C#-compatible JSON |
| `sf-media` | `ScreenForge/Record/VideoGeometry.cs`, `VideoBitrate.cs`, `AudioConvert.cs` | Ported, contract-tested |
| `sf-net` | `ScreenForge/Translate/*`, `Search/ReverseImageSearch.cs`, `Upload/*` | Ported, protobuf byte-identical |
| `sf-edit` | `ScreenForge/Gif/Editing/*`, `Editor/CanvasViewTransform.cs` (pure) | Ported, contract-tested |

Verified: `sf-gif` produces output **byte-for-byte identical** to the C#
encoder across Neural/Octree quantization, Floyd-Steinberg dithering, global vs
local palettes, and transparency. `sf-settings` reads the JSON the C# app writes
and writes JSON the C# app reads back with the same values. The fixtures under
each crate's `tests/fixtures/` are generated by the real C# code
(`ScreenForge.Tests/GoldenGifFixture.cs`, `GoldenSettingsFixture.cs`), not
hand-written.

```
cargo test --workspace    # 92 tests: unit + golden byte-compare + decode round-trip + settings contract
```

Regenerate the golden fixtures after a deliberate encoder or settings change:

```
SF_WRITE_GOLDEN=1 dotnet test ScreenForge.Tests -c Release --filter GoldenGifFixture
SF_WRITE_GOLDEN=1 dotnet test ScreenForge.Tests -c Release --filter GoldenSettingsFixture
```

## Why frame handling is different here

The C# export path materializes every frame as a full BGRA buffer at once
(`GifEditorWindow.Panels.cs:1059`), which is where the multi-GB peaks come from —
not the capture path. `GifFile<W: Write>` is generic over the sink and writes
frames as they arrive, so export streams to a file instead of accumulating. The
frame store keeps frames Deflate-compressed between capture and export.

## Not yet ported

The rest is ordered by how much of it is pure logic. UI (`Windows/`, 8 XAML
windows + themes, ~16.8k lines) is a rewrite, not a port. Platform bindings with
no Rust counterpart: Windows App SDK AI (`SubjectSegmenter`), Velopack
auto-update, Media Foundation + WASAPI recording.
