# ScreenForge — Rust port

Reference implementation of ScreenForge in Rust. Starts with the parts that are
pure logic, where behaviour can be pinned byte-for-byte against the C# original
before anything platform-specific is rewritten.

## Measured memory (the reason for the port)

`Get-Process` on the shipping C# app vs the Rust pipeline, on this machine
(virtual desktop 3383x2160):

| | Working set | Private committed |
|---|---|---|
| C# app, idle | 118 MB | 516 MB |
| Rust CLI, single capture -> PNG | **20.6 MB peak** | - |
| Rust CLI, 8-frame GIF encode | 105 MB peak (one 29 MB frame buffer dominates) | - |

Release binary: **244 KB** (the C# `bin/Release` folder is 329 MB). The GIF path
streams frames through `GifFile<W: Write>`, so it never holds all of them - the
C# export opened every frame as BGRA at once (`GifEditorWindow.Panels.cs:1059`).

Measured baseline for why this exists: the shipping C# app idles at
**~118 MB working set / 516 MB private** (`Get-Process ScreenForge`), which is
framework overhead a tray app shouldn't carry.

Verified: `sf-gif` produces output **byte-for-byte identical** to the C#
encoder across Neural/Octree quantization, Floyd-Steinberg dithering, global vs
local palettes, and transparency. `sf-settings` reads the JSON the C# app writes
and writes JSON the C# app reads back with the same values. The fixtures under
each crate's `tests/fixtures/` are generated by the real C# code
(`ScreenForge.Tests/GoldenGifFixture.cs`, `GoldenSettingsFixture.cs`), not
hand-written.

```

```

## Running it

`sf-cli` proves the pipeline end to end — real screen capture feeding the ported
GIF encoder, no C# involved:

```
cargo run -p sf-cli -- png out.png                 # capture the screen
cargo run -p sf-cli -- crop out.png 100 100 400 300 # a region
cargo run -p sf-cli -- gif out.gif 10 100           # N consecutive captures
cargo run -p sf-cli -- record out.gif 5 10          # 5 s of real-time recording
cargo run -p sf-cli -- settings                     # load %APPDATA% settings
cargo run -p sf-cli -- run                           # tray shell: Alt+Shift+S captures
```

`shot` captures and places the image on the Windows clipboard (CF_DIB) as well as
saving it — verified by reading it back with `Clipboard.GetImage()`.

The `run` command is the interactive path: it registers the global hotkey, then
on each press opens the region picker, crops the selection, copies it to the
clipboard and saves it. Verified by driving it (Ctrl+Shift+F9 to avoid the
running C# app's chord) — one synthesized press, one 229x114 drag, produced a
229x114 clipboard image and a matching PNG.

`record` mirrors the C# recorder's split: capture frames are Deflate-compressed as
they arrive (bounded memory), then exported once with a **global palette** so
per-frame encoding is a cached color map rather than a full NeuQuant pass — the
difference between ~7 s and ~2 min for a 3 s take.

Capture (GDI BitBlt, `windows-rs`) → BGRA → `sf-gif` → valid PNG / GIF89a.
Verified: a live capture encodes to a GIF the third-party `gif` crate decodes
back at the same dimensions (`sf-cli/tests/pipeline.rs`).

Regenerate the golden fixtures after a deliberate encoder or settings change:

```
SF_WRITE_GOLDEN=1 dotnet test ScreenForge.Tests -c Release --filter GoldenGifFixture
SF_WRITE_GOLDEN=1 dotnet test ScreenForge.Tests -c Release --filter GoldenSettingsFixture
```

## Why frame handling is different here

The C# export path materializes every frame as a full BGRA buffer at once
(`GifEditorWindow.Panels.cs:1059`), which is where the multi-GB peaks come from —
not the capture path. `GifFile<W: Write>` is generic over the sink and writes
frames as they arrive, so export streams to a file instead of accumulating. The
frame store keeps frames Deflate-compressed between capture and export.

## Not yet ported

The rest is ordered by how much of it is pure logic. UI (`Windows/`, 8 XAML
windows + themes, ~16.8k lines) is a rewrite, not a port. Platform bindings with
no Rust counterpart: Windows App SDK AI (`SubjectSegmenter`), Velopack
auto-update, Media Foundation + WASAPI recording.
